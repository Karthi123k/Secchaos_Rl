\begin{abstract}
Modern enterprise software systems are increasingly architected as distributed, multi-tier microservice topologies deployed across cloud-native container orchestration environments. While microservice decomposition enhances developer velocity and elasticity, it dramatically expands the operational attack surface and introduces complex dependency failure propagation pathways. Security Chaos Engineering (SCE) proactively uncovers vulnerabilities by intentionally injecting security turbulence into running systems; however, contemporary SCE practices remain overwhelmingly manual, declarative, and open-loop. Furthermore, automating security remediation in live distributed architectures introduces a profound operational dilemma: aggressive mitigations (such as container restarts, credential revocations, or network isolation) frequently trigger cascading transaction timeouts and catastrophic availability collapse.

To bridge this operational divide, this paper presents \textbf{SecChaos-RL}, an autonomous, closed-loop software resilience framework that unifies Security Chaos Engineering with deep reinforcement learning. SecChaos-RL formalizes the runtime mitigation decision problem as a multi-objective Markov Decision Process (MDP) designed to balance security risk reduction, operational availability preservation, recovery speed (Mean Time to Recovery, MTTR), and mitigation cost. The framework introduces a domain-tailored neural policy architecture incorporating Multi-Head Self-Attention over microservice dependency telemetry, Threat-Aware Feature Gating, an Auxiliary Next-Step Risk Prediction Head, and Threat-Adaptive Policy Temperature Exploration. We conduct a rigorous comparative evaluation against deterministic software engineering baselines (No-Mitigation, Static Rule-Based, and DevOps Threshold-Based heuristics) and standard RL algorithms (DQN, A2C, and PPO) across 30 independent random seeds under multi-stage security chaos and cascading failure dynamics. 

Our empirical evaluation and repeated-measures statistical analysis reveal critical operational trade-offs: while static rule-based heuristics achieve high local risk reduction ($55.5\% \pm 4.8\%$) under alert triggers, they induce severe mitigation churn (deploying redundant actions with a $30.8\% \pm 4.9\%$ false mitigation rate, $15.4 \pm 2.5$ wrong actions/ep). In contrast, SecChaos-RL balances multi-objective stability, achieving significantly faster recovery under cascading failure compared to conservative DevOps heuristics ($\text{MTTR} = 1.79 \pm 0.53$ steps vs. $2.29 \pm 0.30$ for Threshold-Based, paired $p_{holm} = 0.0013$; and $2.24 \pm 0.23$ for Queue-Aware Cooldown, paired $p_{holm} = 0.0013$), maintaining superior action selectivity over static rules ($7.5$ vs. $15.4$ wrong actions/ep), and executing decisions in sub-millisecond latency ($0.44 \pm 0.15$\,ms mean, $1.04$\,ms $p_{99}$ on CPU). A systematic six-stage ablation study isolates the contributions of each architectural mechanism, and our findings establish practical deployment boundaries between deterministic heuristics and autonomous reinforcement learning control.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Distributed microservice architectures have become the foundational paradigm for cloud-native enterprise computing, supporting large-scale mission-critical applications in finance, telecommunications, healthcare, and e-commerce~\cite{basiri2016chaos, aderaldo2025declarative, soldani2023microservice}. In contrast to monolithic software, microservice systems decompose enterprise logic into fine-grained, independently deployable services that communicate across lightweight network protocols (e.g., REST, gRPC) and asynchronous message queues~\cite{taibi2021microservice, camacho2022chaos}. While this architectural decoupling enables continuous deployment and organizational scaling, it dramatically magnifies software complexity: real-world service dependency graphs span dozens of interdependent services, creating expansive, porous attack surfaces and nonlinear failure propagation pathways~\cite{esen2025chaos, myrbakken2020security}.

Ensuring continuous software correctness and reliability in hyperscale environments represents a paramount software engineering challenge~\cite{brooker2025systems}. Traditional pre-production software security practices—such as pre-commit static application security testing (SAST), pre-deployment dynamic testing (DAST), automated test plan generation~\cite{haldar2026testplan}, static buffer-overflow vulnerability analysis~\cite{huang2026cotstatic}, bug report classification~\cite{du2024llmbrc}, and opcode slicing-enhanced vulnerability learning~\cite{tong2026osel}—provide vital build-time guarantees. However, these static techniques are fundamentally blind to runtime emergence: they analyze components in isolation and cannot predict how active cyber threats, configuration drifts, and cascading operational degradations interact across interconnected services under live production traffic~\cite{shortridge2023security, owotogbe2025chaos}. Furthermore, adversarial manipulation of software analytics models~\cite{awal2025adversarial} highlights the necessity of validating defensive mechanisms under active, adversarial runtime conditions.

To address this challenge, the software engineering community has embraced \textit{Chaos Engineering}—the discipline of experimenting on a software system to build confidence in its capability to withstand turbulent conditions in production~\cite{basiri2016chaos, rosenthal2020chaos}. Originating with infrastructure-focused tools such as Netflix's Chaos Monkey and evolving into cloud-native platforms like ChaosBlade~\cite{chaosblade2021}, LitmusChaos~\cite{litmus2022}, Gremlin~\cite{gremlin2022}, Chaos Mesh~\cite{chaosmesh2021}, and AWS Fault Injection Simulator~\cite{awsfis2023}, chaos engineering systematically injects physical server crashes, network partitions, and resource exhaustion~\cite{camacho2022chaos, esen2025chaos, baghorn2022fault}. Recently, this methodology has evolved into \textit{Security Chaos Engineering} (SCE)~\cite{shortridge2023security, myrbakken2021security}. Rather than focusing solely on server crashes, SCE injects security-specific turbulence—such as expired TLS certificates, vulnerable third-party dependencies, credential leaks, privilege escalations, and API misconfigurations—to validate defensive controls under adversarial conditions~\cite{myrbakken2021security, bedoya2024enhancing}.

Despite its conceptual promise, current SCE practice exhibits a critical software engineering limitation: \textbf{it operates as an open-loop, human-in-the-loop paradigm}~\cite{owotogbe2025chaos, shortridge2023security}. Faults are injected according to pre-scripted schedules, telemetry is inspected post-experiment, and remediation requires manual engineer intervention. In high-velocity DevSecOps environments, human-driven incident response is too slow to mitigate automated attacks that exploit transient chaos windows within seconds~\cite{shortridge2023security, liu2025autonomous}.

However, attempting to automate security mitigation in live microservices introduces a fundamental operational conflict:
\begin{itemize}
    \item \textbf{The Security vs. Availability Dilemma:} Applying immediate, aggressive security mitigations—such as terminating suspicious pods, blocking network routes, revoking credentials, or rolling back service configurations—frequently causes severe operational disruption. In tightly coupled microservice topologies, killing an authentication or inventory service triggers upstream timeout storms, circuit-breaker trips, and cascading transaction failures, converting a localized security fault into a catastrophic availability outage~\cite{aderaldo2025declarative, schneider2015survey}.
    \item \textbf{Failure of Static and Heuristic Rules:} In production systems, software engineers frequently rely on deterministic alert-matching scripts (e.g., ``if certificate alert detected, execute certificate rotation''). Under concurrent faults and high background traffic, naive rules suffer from alert flapping and mitigation storms: multiple services deploy simultaneous mitigations, exhausting cluster CPU and memory, multiplying operational delays, and degrading request throughput~\cite{schneider2015survey}.
\end{itemize}

Self-adaptive software systems (SASS) and autonomic computing frameworks provide an established theoretical foundation for closed-loop self-healing through the classic MAPE-K (Monitor, Analyze, Plan, Execute, Knowledge) loop~\cite{salehie2009self, garlan2004rainbow, schneider2015survey}. Reinforcement learning (RL) has emerged as an attractive candidate for the ``Plan'' phase, allowing autonomous agents to learn multi-objective control policies through trial-and-error interaction with a dynamic environment~\cite{sutton1998reinforcement, mnih2015human}. While deep reinforcement learning (DRL) has demonstrated remarkable success in complex domains~\cite{silver2016mastering, mnih2016asynchronous} and standardized benchmarking suites~\cite{towers2026gymnasium, raffin2021stable}, applying standard RL algorithms (such as DQN~\cite{mnih2015human}, A2C~\cite{mnih2016asynchronous}, or standard PPO~\cite{schulman2017ppo}) directly to microservice security mitigation fails in practice. Standard RL policies lack domain-specific awareness of microservice topologies, treat all telemetry dimensions homogeneously, struggle with delayed mitigation execution effects, and frequently destabilize live services through exploratory actions during critical attack spikes~\cite{zheng2025proximal, standen2021cyborg, nguyen2021deep, xiao2018iot}. Emerging research on Large Language Models (LLMs) for software engineering~\cite{hou2024large} similarly underscores that without closed-loop execution verification, design-time advice cannot govern runtime microservice safety.

\subsection{Research Questions}
To address these technical challenges and deliver a practically useful software contribution, this paper formulates and investigates four core Research Questions (RQs):
\begin{itemize}
    \item \textbf{RQ1 (Resilience and Recovery Efficacy):} How effectively does SecChaos-RL reduce systemic security risk and minimize mean time to recovery (MTTR) compared to deterministic software engineering baselines (No-Mitigation, Static Rule-Based, Threshold-Based) and standard RL algorithms (DQN, A2C, PPO)?
    \item \textbf{RQ2 (Operational Availability and Trade-Off Balance):} How well does SecChaos-RL preserve live microservice availability and prevent false mitigation storms when subjected to concurrent security faults and cascading dependency failures?
    \item \textbf{RQ3 (Architectural Ablation and Component Contributions):} What are the isolated contributions of the individual framework components—multi-objective reward design, multi-head self-attention, auxiliary risk prediction, threat-aware gating, and adaptive policy temperature—to overall system survivability?
    \item \textbf{RQ4 (Computational Overhead and Practical Feasibility):} What is the runtime decision latency and computational overhead of SecChaos-RL, and does it satisfy the real-time execution constraints required for cloud-native microservice orchestration?
\end{itemize}

\subsection{Main Contributions}
This paper makes the following concrete contributions to the software engineering and microservice resilience literature:
\begin{enumerate}
    \item \textbf{Software Engineering Framework Contribution:} We design and implement SecChaos-RL, an open, modular Python framework that operationalizes closed-loop Security Chaos Engineering. The architecture decouples continuous Poisson fault injection (\texttt{ChaosEngine}), service dependency DAG propagation (\texttt{DependencyTopology}), threat-aware decision orchestration (\texttt{ThreatAwareOrchestrator}), asynchronous mitigation action execution with queuing and transient delays (\texttt{MitigationExecutor}), and reproducible statistical benchmarking (\texttt{BenchmarkHarness}).
    \item \textbf{Algorithmic Reinforcement Learning Contribution:} We formalize the microservice mitigation problem as a multi-objective Markov Decision Process (MDP). To address the challenges of correlated telemetry and delayed execution feedback, we introduce a domain-tailored neural policy architecture incorporating Multi-Head Self-Attention over dependency features, Threat-Aware Feature Gating (amplifying vulnerability signals during active compromise), an Auxiliary Risk Prediction Head (regularizing latent representations against future state transitions), and Threat-Adaptive Policy Temperature Exploration.
    \item \textbf{Formal Algorithmic Workflows:} We provide complete, mathematically rigorous algorithmic workflows for both closed-loop runtime mitigation execution (Algorithm~\ref{alg:secchaos_execution}) and threat-aware policy optimization with auxiliary risk regularization (Algorithm~\ref{alg:policy_training}).
    \item \textbf{Rigorous Comparative Evaluation Across 30 Seeds:} We conduct an extensive empirical evaluation across 30 independent random seeds, benchmarking SecChaos-RL against deterministic software heuristics (No-Mitigation, Static Rule-Based, Threshold-Based, and Queue-Aware Cooldown heuristics) and standard RL algorithms (DQN, A2C, standard PPO). Using repeated-measures ANOVA and paired hypothesis testing, we rigorously characterize the operational trade-offs between heuristic rule triggering and reinforcement learning control.
    \item \textbf{Six-Stage Ablation and Hardware Profiling:} We execute a six-stage ablation study isolating the marginal contributions of each architectural component (reward shaping, self-attention, auxiliary risk prediction, threat-aware gating, and adaptive temperature exploration), and profile runtime decision latency ($0.44 \pm 0.15$\,ms mean, $1.04$\,ms $p_{99}$ on CPU) to assess practical deployability in cloud-native container environments.
    \item \textbf{Complete, Verifiable Replication Package:} We provide a self-contained, open-source replication package containing the entire simulator environment, agent implementations, evaluation scripts, raw CSV telemetry across all 30 seeds, and automated analysis code to ensure full reproducibility.
\end{enumerate}

\section{Background and Related Work}
\label{sec:related_work}

This section reviews related research across four key areas: Chaos Engineering, Microservice Resiliency Benchmarking, Security Chaos Engineering, and Autonomous Reinforcement Learning for Cyber Defense.

\subsection{Chaos Engineering and Distributed Fault Injection}
Chaos Engineering was established as a disciplined practice by Netflix engineers to verify the reliability of large-scale distributed cloud applications~\cite{basiri2016chaos}. Rosenthal and Jones synthesized core industry practices, emphasizing the necessity of automating experiments, minimizing blast radiuses, and running continuous turbulence campaigns in production~\cite{rosenthal2020chaos}. A comprehensive multi-vocal literature review by Owotogbe et al.~\cite{owotogbe2025chaos} analyzed 96 academic and industrial sources, formalizing a taxonomy of chaos engineering platforms across execution environments, automation modes, and target architectures. Esen et al.~\cite{esen2025chaos} systematically reviewed chaos experiments in microservices across 31 papers and 38 tools, noting that mainstream tooling (e.g., Chaos Mesh~\cite{chaosmesh2021}, Gremlin~\cite{gremlin2022}, ChaosBlade~\cite{chaosblade2021}, LitmusChaos~\cite{litmus2022}, and AWS FIS~\cite{awsfis2023}) focuses overwhelmingly on physical and network faults—such as packet latency, CPU stress, and container restarts—while neglecting security-specific compromise states. Bagehorn et al.~\cite{baghorn2022fault} demonstrated fault injection platforms for training AIOps models, yet focused on operational anomalies rather than adversarial attack mitigations.

Addressing the need for structured, configurable fault injection platforms, Camacho et al.~\cite{camacho2022chaos} introduced \textit{Chaos as a Software Product Line} (CoSPL) in \textit{Software: Practice and Experience}. Their platform, \textit{Pystol}, models fault injection capabilities as software product line features across open hybrid-cloud environments (e.g., OpenShift and Kubernetes). While CoSPL demonstrates the software engineering value of configurable chaos architectures, its execution remains declarative and open-loop: it verifies system tolerance against pre-scripted variations but lacks an autonomous, learning-based runtime mitigation engine.

\subsection{Microservice Resiliency Benchmarking and Self-Healing}
In distributed microservice systems, resilience patterns—such as timeouts, retries, fallbacks, and circuit breakers—are standard software engineering mechanisms to mitigate transient degradations~\cite{aderaldo2025declarative, schneider2015survey, soldani2023microservice}. Taibi et al.~\cite{taibi2021microservice} analyzed microservice API evolution patterns in \textit{Software: Practice and Experience}, emphasizing that service interface drift and asynchronous call coupling create fragile dependency chains.

In a landmark study published in \textit{Software: Practice and Experience}, Aderaldo et al.~\cite{aderaldo2025declarative} presented \textit{ResilienceBench}, a declarative benchmarking approach and Kubernetes operator tool designed for the controlled evaluation of microservice resiliency patterns under simulated failures (tested on Google Online Boutique). Their work demonstrates that naive retry configurations amplify cascading service failures and increase tail latency during downstream disruptions.

Self-healing systems literature provides the broader control-theoretic foundation for autonomous software resilience. In their seminal survey in \textit{Software: Practice and Experience}, Schneider, Barker, and Dobson~\cite{schneider2015survey} categorized multi-tier self-healing frameworks using the autonomic MAPE-K control loop~\cite{garlan2004rainbow, salehie2009self}. They highlighted that while rule-based self-healing loops succeed in isolated components, they exhibit severe stability issues when managing multi-tier dependencies subject to concurrent, overlapping disturbances. SecChaos-RL directly builds upon this insight: rather than using static rule heuristics that fight one another, it employs a centralized, threat-aware RL policy to coordinate multi-service mitigations.

\subsection{Security Chaos Engineering (SCE) and DevSecOps}
Security Chaos Engineering applies the empirical philosophy of chaos experimentation directly to cyber resilience~\cite{shortridge2023security}. Myrbakken and Colomo-Palacios~\cite{myrbakken2020security} reviewed security bottlenecks in DevSecOps pipelines, concluding that traditional pre-production testing fails to keep pace with continuous deployment agility. In subsequent work, Myrbakken et al.~\cite{myrbakken2021security} formalized SCE as a continuous assessment paradigm, demonstrating how automated security fault injection exposes configuration drifts and access control weaknesses.

Shortridge and Rinehart~\cite{shortridge2023security} detailed the principles of SCE, arguing that complex software systems are fundamentally non-deterministic and that resilience depends on validating system behavior under active attack conditions. Bedoya et al.~\cite{bedoya2024enhancing} demonstrated the integration of SCE with Large Language Models (LLMs) to discover architectural threat vectors during the design phase of a commercial retail application. However, existing SCE tools remain limited to passive vulnerability discovery: they detect when a system fails a security property, but rely entirely on human engineers to craft and execute mitigations~\cite{shortridge2023security, owotogbe2025chaos}.

\subsection{Reinforcement Learning for Cyber Defense and Mitigation}
Reinforcement learning has demonstrated significant capability in complex decision-making domains~\cite{silver2016mastering, sutton1998reinforcement}. Value-based methods (e.g., Deep Q-Networks~\cite{mnih2015human}) and policy gradient approaches (e.g., Advantage Actor-Critic~\cite{mnih2016asynchronous} and Proximal Policy Optimization~\cite{schulman2017ppo}) have enabled autonomous agents to learn sophisticated control strategies in high-dimensional state spaces.

In cybersecurity, deep reinforcement learning (DRL) has been applied to intrusion detection, cyber-physical defense, IoT protection~\cite{xiao2018iot}, and autonomous penetration testing~\cite{nguyen2021deep, liu2025autonomous}. Standen et al.~\cite{standen2021cyborg} introduced \textit{CybORG}, a Gym-based simulation environment for training autonomous cyber defense agents in Security Operations Centers (SOCs). However, CybORG assumes static enterprise network topologies and fixed IP routing graphs, omitting microservice dependency cascades, runtime HTTP/gRPC request availability, and chaos-driven operational trade-offs. Algorithmic enhancements, such as Reward-based Prioritization PPO (RP-PPO) by Zheng et al.~\cite{zheng2025proximal}, have improved sample efficiency, but remain unspecialized for the dual constraints of security isolation and service continuity. Standard frameworks such as Gymnasium~\cite{towers2026gymnasium} and Stable-Baselines3~\cite{raffin2021stable} provide standardized algorithmic baselines, which we leverage and extend for microservice security control.

\section{SecChaos-RL Framework Architecture}
\label{sec:architecture}

SecChaos-RL is designed as an extensible, closed-loop software architecture implementing the classic MAPE-K self-adaptation paradigm~\cite{salehie2009self, garlan2004rainbow}. The framework operates in discrete operational time steps, continuously observing telemetry from monitored microservices, injecting controlled security chaos, inferring optimal mitigation decisions, and asynchronously executing remediations.

\begin{figure}[!htbp]
\centering
\includegraphics[height=0.38\textheight, keepaspectratio]{figs/workflow.jpg}
\caption{SecChaos-RL Closed-Loop Software Architecture: Interaction between the monitored microservice dependency topology, the Security Chaos Engine, telemetry collection, the threat-aware deep RL orchestrator, and the asynchronous mitigation executor.}
\label{fig:framework_architecture}
\end{figure}

As illustrated in Figure~\ref{fig:framework_architecture}, SecChaos-RL is composed of five decoupled, modular software components:

\begin{enumerate}
    \item \textbf{Monitored Microservice Topology (\texttt{DependencyTopology}):} Represents the operational target system structured as a directed acyclic graph (DAG) $\mathcal{G} = (\mathcal{V}, \mathcal{E})$. Each node $v \in \mathcal{V}$ models an individual microservice maintaining local security risk $r_t(v) \in [0, 1]$ and service availability $a_t(v) \in [0, 1]$. Directed edges $(u, v) \in \mathcal{E}$ represent synchronous downstream API call dependencies (e.g., the Gateway depends on Authentication, which depends on the User service).
    \item \textbf{Security Chaos Engine (\texttt{ChaosEngine}):} Implements dynamic, stochastic security fault injection across eight standardized vulnerability categories. The engine generates faults according to configurable Poisson arrival processes and assigns random severities and operational durations. It models active attacker exploitation by tracking concurrent attack sessions that target vulnerable services.
    \item \textbf{Telemetry and State Monitor (\texttt{StateMonitor}):} Continuously inspects the microservice cluster, aggregating individual service risks, resource metrics (CPU utilization, memory consumption, network overhead), transaction success ratios, and MTTR tracking into a standardized 16-dimensional observation vector $o_t \in \mathbb{R}^{16}$.
    \item \textbf{Threat-Aware Decision Orchestrator (\texttt{ThreatAwareOrchestrator}):} The intelligence engine of the framework, implementing our specialized deep actor-critic policy. It ingests the observation vector, computes multi-head self-attention across features, gates security dimensions based on active threat severity, and selects a mitigation action $a_t \in \mathcal{A}$.
    \item \textbf{Asynchronous Mitigation Executor (\texttt{MitigationExecutor}):} Translates abstract policy actions into operational operations (e.g., certificate rotation, dependency patching, RBAC policy restriction). Crucially, the executor models real-world operational delays: actions are placed in an asynchronous execution queue, requiring $\tau \in \{0, 1, 2\}$ operational steps to complete, while consuming transient CPU and memory resources during deployment. Upon completion, the executor actively invokes service healing in the dependency graph, reducing service risk and restoring availability.
\end{enumerate}

\section{Threat Model and Decision Methodology}
\label{sec:methodology}

\subsection{Threat Model and Fault Taxonomy}
We assume an adversarial environment where an external attacker continuously probes public-facing entry points (e.g., API Gateway) and attempts lateral movement across internal microservices. The attacker seeks to exploit unpatched dependencies, leaked secrets, or misconfigured access permissions to compromise data integrity, escalate privileges, and exhaust system resources.

Table~\ref{tab:fault_categories} formalizes the eight security fault categories modeled in SecChaos-RL, mapped to their target services. When a fault $f_i$ with severity $\sigma_i \in [0.35, 0.65]$ is injected into service $u \in \mathcal{V}$, the service's risk is immediately incremented:
\begin{equation}
    r_{t+1}(u) \leftarrow \min\left(1.0, r_t(u) + \sigma_i\right), \quad a_{t+1}(u) \leftarrow \max\left(0.0, a_t(u) - 0.12 \cdot \sigma_i\right)
\end{equation}
If the service's risk crosses the critical degradation threshold ($r_t(u) > 0.35$), cascading failure propagates along all outgoing edges $(u, v) \in \mathcal{E}$:
\begin{align}
    r_{t+1}(v) &\leftarrow \min\left(1.0, r_t(v) + \alpha_{casc} \cdot r_t(u) \cdot \gamma_{coupl}\right) \\
    a_{t+1}(v) &\leftarrow \max\left(0.0, a_t(v) - 0.12 \cdot \left[\alpha_{casc} \cdot r_t(u) \cdot \gamma_{coupl}\right]\right)
\end{align}
where $\alpha_{casc} = 0.22$ and $\gamma_{coupl} = 0.5$ represent the cascading propagation coefficient and inter-service coupling factor, respectively.

\subsection{Markov Decision Process (MDP) Formulation}

\begin{align}
    \mathbf{s}_t = \big[ & r_t^{cert}, r_t^{dep}, r_t^{sec}, r_t^{rbac}, r_t^{auth}, \mathcal{L}_{threat}, \mathcal{V}_{score}, A_{act}^{norm}, \nonumber \\
    & u_{cpu}, u_{mem}, u_{net}, a_t, t_{rec}^{norm}, \bar{h}_{atk}, \eta_{prev}, |\mathcal{F}_{act}|^{norm} \big]^T \in [0, 1]^{16}
\end{align}

\subsubsection{Action Space, Execution Queues, and Transition Semantics}
The action space $\mathcal{A}$ comprises nine discrete operational mitigations:
\begin{align}
    \mathcal{A} = \{ & a_0: \text{ignore/idle}, a_1: \text{rotate\_cert}, a_2: \text{patch\_dep}, \nonumber \\
    & a_3: \text{rotate\_secret}, a_4: \text{restrict\_rbac}, a_5: \text{enable\_mfa}, \nonumber \\
    & a_6: \text{security\_patch}, a_7: \text{revoke\_priv}, a_8: \text{rollback} \}
\end{align}
Each mitigation action $a_k \in \mathcal{A}$ is parameterized by target fault codes, an asynchronous execution delay $d_k \in \{0, 1, 2\}$ steps, invocation cost $C(a_k)$, and transient resource overheads ($\Delta u_{cpu}, \Delta u_{mem}, \Delta u_{net}$):
\begin{itemize}
    \item $a_0$ (ignore): Cost $0.0$, delay $d_0 = 0$, overheads $(0.0, 0.0, 0.0)$, targets none.
    \item $a_1$ (rotate\_cert): Cost $0.10$, delay $d_1 = 1$, overheads $(0.02, 0.01, 0.01)$, targets $\{F1, F8\}$.
    \item $a_2$ (patch\_dep): Cost $0.40$, delay $d_2 = 2$, overheads $(0.15, 0.10, 0.05)$, targets $\{F2, F7\}$.
    \item $a_3$ (rotate\_secret): Cost $0.20$, delay $d_3 = 1$, overheads $(0.05, 0.03, 0.02)$, targets $\{F3\}$.
    \item $a_4$ (restrict\_rbac): Cost $0.15$, delay $d_4 = 1$, overheads $(0.03, 0.02, 0.01)$, targets $\{F4, F6\}$.
    \item $a_5$ (enable\_mfa): Cost $0.10$, delay $d_5 = 0$, overheads $(0.01, 0.01, 0.01)$, targets $\{F5\}$.
    \item $a_6$ (apply\_patch): Cost $0.50$, delay $d_6 = 2$, overheads $(0.20, 0.15, 0.05)$, targets $\{F7, F2\}$.
    \item $a_7$ (revoke\_priv): Cost $0.20$, delay $d_7 = 1$, overheads $(0.04, 0.03, 0.01)$, targets $\{F6, F4\}$.
    \item $a_8$ (rollback): Cost $0.35$, delay $d_8 = 1$, overheads $(0.10, 0.08, 0.03)$, targets $\{F8, F1\}$.
\end{itemize}

\textbf{Asynchronous Queue and Operational Action Outcomes:} In live microservice operations, automated interventions interact with non-deterministic failure dynamics across three distinct operational states:
\begin{enumerate}
    \item \textbf{Unnecessary Dispatch ($N_{wrong}$):} An action $a_t \ne 0$ is dispatched when neither an active fault matches its target codes nor the target service exhibits elevated vulnerability ($r_{target} \le 0.30$). Such actions reflect false alarms or policy churn and directly contribute to the False Mitigation Rate ($\text{FMR} = N_{wrong} / \max(1, N_{actions})$). The previous mitigation efficacy indicator $\eta_{prev}$ drops to $0.2$, and the agent incurs an operational penalty $\beta_4 \mathcal{P}_{wrong}$.
    \item \textbf{Queue Redundancy ($N_{redundant}$):} An action was valid when dispatched (matching an active fault or elevated risk), but during its asynchronous queue latency $d_k$, an earlier maturing mitigation or natural fault expiration resolved the underlying fault. Upon maturity ($t_{due} = t + d_k$), the action executes but finds no matching active fault. Such actions represent unavoidable queuing latency artifacts rather than controller misclassifications; they consume transient resource overheads ($\Delta u_{cpu}, \Delta u_{mem}, \Delta u_{net}$) without altering service health.
    \item \textbf{Transient Execution Failure ($N_{drop}$):} To model transient cloud-native RPC timeouts, pod scheduling delays, or admission control rejections, dispatched mitigations face an empirical $8\%$ transient failure rate ($92\%$ successful queue admission). Dropped actions incur invocation cost without entering the queue $\mathcal{Q}$.
\end{enumerate}

Within each discrete simulation step $t$, operations proceed in the following strict order:
\begin{enumerate}
    \item \textit{Action Queue Processing \& Dispatch:} Actions whose delay has expired ($t_{due} \le t$) are dequeued and executed, invoking active service healing ($\Delta r = -0.80 \times severity$, restoring availability by $+0.15 \times severity$). If multiple queued mitigations target the same fault, the first execution clears the fault; subsequent duplicate actions find no remaining fault and are recorded as queue redundancies.
    \item \textit{Continuous Chaos Injection:} New security faults are injected via Poisson arrivals governed by curriculum difficulty ($p_{fault} = 0.12 + 0.08 \times level$).
    \item \textit{Fault Expiration \& Natural Healing:} Faults exceeding their duration $d_f$ expire naturally, and unattacked services experience natural baseline recovery.
    \item \textit{Dependency Cascade Propagation:} Degraded upstream nodes in $\mathcal{G}$ ($r_u > 0.35$) propagate non-linear degradation to downstream dependencies: $\Delta r_v = 0.22 \times r_u \times \gamma_{coupl}$.
    \item \textit{Threat Severity \& Attack Execution:} Systemic vulnerability score $\mathcal{V}_{score}$ and threat severity $\mathcal{L}_{threat}$ are updated; active attacks launch probabilistically and inflict collateral risk spikes ($+0.08 \times A_{act}$).
    \item \textit{Telemetry and Availability Computation:} Resource utilizations are updated including active action overheads, and live service availability $a_{t+1}$ is evaluated against resource bottlenecks and graph topology.
    \item \textit{Recovery and MTTR Tracking:} If $a_{t+1} < 0.90$ or $\mathcal{V}_{score} > 0.45$, degradation duration increments; once restored, the completed recovery step interval is logged.
    \item \textit{Multi-Objective Reward Evaluation:} The transition reward $R_t$ is computed and clipped to $[-8.0, 8.0]$.
\end{enumerate}
This sequence guarantees that live cascading failures and delayed mitigations realistically interact: mitigations do not take effect until their queue delay elapses, and the agent observes ongoing versus completed interventions via the operational telemetry vector.

\subsubsection{Multi-Objective Reward Function}
The composite reward function balances security risk reduction, operational availability preservation, rapid recovery, and resource efficiency while penalizing service disruption:
\begin{align}
    R_t = & \; \alpha_1 \Delta \mathcal{L}_{sec} + \alpha_2 \Delta \mathcal{L}_{threat} + \alpha_3 \mathcal{L}_{avail} + \alpha_4 \mathcal{L}_{rec} + \alpha_5 \mathcal{L}_{eff} + \alpha_6 \mathcal{L}_{cont} \nonumber \\
    & - \beta_1 \mathcal{P}_{atk} - \beta_2 \mathcal{P}_{delay} - \beta_3 \mathcal{P}_{res} - \beta_4 \mathcal{P}_{wrong} + \mathcal{R}_{mit}
    \label{eq:reward_function}
\end{align}
The exact numerical reward coefficients and their operational bounds are specified as follows:
\begin{itemize}
    \item $\alpha_1 = 4.5$ ($\alpha_{risk}$): Multiplier for local risk reduction $\Delta \mathcal{L}_{sec} = \bar{r}_t - \bar{r}_{t+1} \in [-1.0, 1.0]$.
    \item $\alpha_2 = 3.5$ ($\alpha_{threat}$): Multiplier for threat severity reduction $\Delta \mathcal{L}_{threat} = \mathcal{L}_{threat}(t) - \mathcal{L}_{threat}(t+1) \in [-1.0, 1.0]$.
    \item $\alpha_3 = 3.0$ ($\alpha_{avail}$): Multiplier for live availability preservation $\mathcal{L}_{avail} = a_{t+1} \in [0.0, 1.0]$.
    \item $\alpha_4 = 1.5$ ($\alpha_{rec}$): Multiplier for recovery immediacy $\mathcal{L}_{rec} = \frac{1}{1 + t_{rec}} \in [0.0, 1.0]$ when $a_{t+1} \ge 0.90$.
    \item $\alpha_5 = 0.5$ ($\alpha_{eff}$): Multiplier for resource efficiency $\mathcal{L}_{eff} = 1 - \frac{u_{cpu} + u_{mem} + u_{net}}{3} \in [0.0, 1.0]$.
    \item $\alpha_6 = 1.5$ ($\alpha_{cont}$): Multiplier for SLA continuity $\mathcal{L}_{cont} = \mathbf{1}[a_{t+1} \ge 0.95] \in \{0, 1\}$.
    \item $\beta_1 = 1.2$ ($\beta_{atk}$): Penalty for successful adversary compromise $\mathcal{P}_{atk} \in \{0, 1\}$.
    \item $\beta_2 = 0.05$ ($\beta_{delay}$): Penalty for prolonged recovery delay $\mathcal{P}_{delay} = t_{rec} / 10 \in [0.0, 2.0]$.
    \item $\beta_3 = 0.25$ ($\beta_{res}$): Penalty for resource utilization spikes exceeding $85\%$ ($\mathcal{P}_{res} \in \{0, 1\}$).
    \item $\beta_4 = 0.30$ ($\beta_{wrong}$): Penalty for deploying unnecessary or mismatched mitigations ($\mathcal{P}_{wrong} \in \{0, 1\}$).
\end{itemize}

To overcome the temporal credit assignment bottleneck caused by asynchronous execution delays, $\mathcal{R}_{mit}$ provides immediate decision-step feedback:
\begin{equation}
    \mathcal{R}_{mit} = \begin{cases}
        +2.4 \cdot \max(0.4, r_{target}) & \text{if } a_t \neq 0 \text{ targets elevated risk } (r_{target} > 0.30), \\
        -1.6 & \text{if } a_t \neq 0 \text{ is redundant or unnecessary}, \\
        -2.0 \cdot \bar{r}_t & \text{if } a_t = 0 \text{ and systemic risk is elevated } (\bar{r}_t > 0.38), \\
        +0.6 & \text{if } a_t = 0 \text{ and the system is healthy.}
    \end{cases}
\end{equation}
The total scalar reward $R_t$ is clipped to the interval $[-8.0, 8.0]$ to prevent gradient explosion during cascading failure spikes. The weights were established a priori following standard Site Reliability Engineering (SRE) priorities: security risk suppression and service uptime dominate ($\alpha_1 + \alpha_2 + \alpha_3 = 11.0$), while recovery speed and continuity ensure operational stability without inducing action thrashing.

\subsection{Deep Policy Architecture and Training Dynamics}
SecChaos-RL implements a specialized neural policy designed to handle correlated microservice telemetry under high turbulence (Figure~\ref{fig:network_architecture}):

\begin{figure}[!t]
\centering
\includegraphics[width=0.78\columnwidth]{figs/network_architecture.jpg}
\caption{Threat-Aware Neural Network Architecture: Multi-Head Self-Attention over projected state embeddings, Threat-Aware Feature Gating, Auxiliary Risk Prediction, and Actor-Critic heads.}
\label{fig:network_architecture}
\end{figure}

\begin{enumerate}
    \item \textbf{Linear Feature Projection:} Each scalar observation dimension $s_t^{(i)} \in \mathbf{s}_t$ ($i \in \{0, \ldots, 15\}$) is projected into an embedding space $\mathbf{e}_t^{(i)} \in \mathbb{R}^{32}$:
    \begin{equation}
        \mathbf{e}_t^{(i)} = \mathbf{W}_e^{(i)} s_t^{(i)} + \mathbf{b}_e^{(i)}, \quad i \in \{0, \ldots, 15\}
    \end{equation}
    \item \textbf{Threat-Aware Feature Gating:} Security-relevant risk dimensions ($i \in \{0, \ldots, 4\}$) are dynamically amplified based on the current global threat severity $\mathcal{L}_{threat}$:
    \begin{equation}
        \mathbf{g}_t^{(i)} = \begin{cases}
            \mathbf{e}_t^{(i)} \cdot \left(1.0 + \mathcal{L}_{threat}\right) & \text{if } i \le 4 \\
            \mathbf{e}_t^{(i)} & \text{otherwise}
        \end{cases}
    \end{equation}
    This prevents secondary operational metrics (such as minor memory fluctuations) from distracting the policy during active security emergencies.
    \item \textbf{Multi-Head Self-Attention:} The gated embedding matrix $\mathbf{X}_t = [\mathbf{g}_t^{(0)}; \ldots; \mathbf{g}_t^{(15)}] \in \mathbb{R}^{16 \times 32}$ is processed by a 2-head self-attention module~\cite{vaswani2017attention} ($d_k = 16$) to learn non-local correlations across service dependencies:
    \begin{equation}
        \text{Attention}(\mathbf{Q}, \mathbf{K}, \mathbf{V}) = \text{softmax}\left(\frac{\mathbf{Q}\mathbf{K}^T}{\sqrt{d_k}}\right)\mathbf{V}, \quad \text{MHA}(\mathbf{X}_t) = \text{Concat}(\text{head}_1, \text{head}_2) \mathbf{W}^O
    \end{equation}
    The flattened attention output passes through feed-forward layers ($512 \rightarrow 256 \rightarrow 128$) with Tanh activations to yield latent representation $\mathbf{z}_t \in \mathbb{R}^{128}$.
    \item \textbf{Actor and Critic Heads:} The actor head (Linear(128, 9), gain 0.01) generates unnormalized action logits $\mathbf{l}_t \in \mathbb{R}^9$. The critic head (Linear(128, 1)) predicts scalar state value $V(\mathbf{s}_t)$.
    \item \textbf{Auxiliary Next-Step Risk Prediction Head (Training Only):} To regularize latent features and accelerate convergence, an auxiliary linear head predicts next-step service risks and availability:
    \begin{equation}
        \hat{\mathbf{y}}_{t+1} = \mathbf{W}_{aux} \mathbf{z}_t + \mathbf{b}_{aux} \in \mathbb{R}^6
    \end{equation}
    trained against ground-truth targets $\mathbf{y}_{t+1}^* = [\mathbf{r}_{t+1}^{(0:4)}, a_{t+1}]^T \in [0, 1]^6$ with MSE loss $\mathcal{L}_{aux}$ and weight $c_2 = 0.25$. Crucially, \textbf{the auxiliary head serves strictly as an inductive regularizer during training}; it is detached during inference and incurs zero runtime computational overhead.
    \item \textbf{Threat-Adaptive Policy Temperature Exploration:} Action selection during training rollout is governed by an adaptive temperature $\tau_{temp}$:
    \begin{equation}
        \pi_\theta(a|\mathbf{s}_t) = \text{softmax}\left(\frac{\mathbf{l}_t(a)}{\tau_{temp}(\mathbf{s}_t)}\right), \quad \tau_{temp}(\mathbf{s}_t) = \max\left(0.2, 1.0 - 0.50 \cdot \mathcal{L}_{threat}\right)
    \end{equation}
    Under quiescent conditions ($\mathcal{L}_{threat} \approx 0, \tau_{temp} = 1.0$), the policy explores diverse actions stochastically. Under critical compromise ($\mathcal{L}_{threat} \approx 1.0, \tau_{temp} \to 0.5$), the temperature drops, forcing the agent to sample deterministically from its learned safety-optimal policy, preventing catastrophic exploration during live attacks. The temperature-scaled probabilities are identically evaluated in the PPO likelihood ratio $r_t(\theta) = \frac{\pi_\theta(a_t | \mathbf{s}_t)}{\pi_{\theta_{old}}(a_t | \mathbf{s}_t)}$, preserving mathematical consistency. During final evaluation, deterministic greedy selection ($\text{argmax}$) is deployed.
\end{enumerate}

\textbf{Optimization Hyperparameters:} The policy is optimized using the Adam optimizer with a learning rate $\eta = 3 \times 10^{-4}$, rollout buffer size $M = 32$ steps, $K = 4$ epochs per update, discount factor $\gamma = 0.99$, Generalized Advantage Estimation (GAE) factor $\lambda = 0.95$, PPO clip threshold $\epsilon = 0.2$, value function loss coefficient $c_1 = 0.5$, auxiliary loss coefficient $c_2 = 0.25$, and entropy regularizer weight $\beta_{ent} = 0.03$.

\subsection{Formal Algorithmic Workflows}
The complete operational lifecycle of SecChaos-RL is formalized in Algorithm~\ref{alg:secchaos_execution} (runtime closed-loop execution) and Algorithm~\ref{alg:policy_training} (policy optimization).

\begin{algorithm}[!htbp]
\caption{SecChaos-RL Closed-Loop Mitigation and Healing Execution}
\label{alg:secchaos_execution}
\begin{algorithmic}[1]
\Require Microservice topology $\mathcal{G} = (\mathcal{V}, \mathcal{E})$, trained policy $\pi_\theta$, value network $V_\phi$, action queue $\mathcal{Q} \leftarrow \emptyset$, maximum steps $T$.
\Ensure Logged episode telemetry and resilience trajectory $\mathcal{T}$.
\State Initialize microservice health: $r(v) \leftarrow r_0(v), a(v) \leftarrow 1.0, \forall v \in \mathcal{V}$
\State Initialize active faults $\mathcal{F} \leftarrow \emptyset$, active attacks $A \leftarrow 0$, step counter $t \leftarrow 0$
\While{$t < T$ \textbf{and} system not collapsed}
    \State $t \leftarrow t + 1$
    \State Observe telemetry vector $\mathbf{s}_t \in \mathbb{R}^{16}$ via \texttt{StateMonitor}
    \State Compute global threat severity $\mathcal{L}_{threat} \leftarrow \frac{1}{1 + \exp[-6.0(\mathcal{V}_{score} - 0.40)]}$
    \State Compute adaptive temperature $\tau_{temp} \leftarrow \max(0.2, 1.0 - 0.50 \cdot \mathcal{L}_{threat})$
    \State Select mitigation action $a_t \sim \pi_\theta(\cdot \mid \mathbf{s}_t, \tau_{temp})$
    \If{$a_t \neq 0$}
        \State Retrieve action specification: delay $d_{a_t} \in \{0, 1, 2\}$, overheads $(\Delta u_{cpu}, \Delta u_{mem}, \Delta u_{net})$
        \State Enqueue pending mitigation: $\mathcal{Q} \leftarrow \mathcal{Q} \cup \{(t + d_{a_t}, a_t)\}$
    \EndIf
    \State Extract due actions: $\mathcal{D}_t \leftarrow \{(t_{due}, a) \in \mathcal{Q} \mid t_{due} \le t\}$; $\mathcal{Q} \leftarrow \mathcal{Q} \setminus \mathcal{D}_t$
    \For{each action $a \in \mathcal{D}_t$}
        \For{each target fault code $c \in \text{targets}(a)$}
            \State Remove resolved fault from active set: $\mathcal{F} \leftarrow \mathcal{F} \setminus \{f \in \mathcal{F} \mid f.code = c\}$
            \State Invoke active graph healing: \texttt{heal\_service}(target($c$), severity)
        \EndFor
    \EndFor
    \State Stochastic fault injection: sample $f_{new} \sim \text{Poisson}(\lambda_{fault})$; apply fault to target service
    \State Cascading failure propagation: update downstream nodes $(u, v) \in \mathcal{E}$ with $r(u) > 0.35$
    \State Update operational resource utilization $u_{cpu}, u_{mem}, u_{net}$ and service availability $a_t$
    \State Compute multi-objective reward $R_t$ via Eq.~(\ref{eq:reward_function})
\EndWhile
\State \Return Execution trajectory $\mathcal{T} = \{(\mathbf{s}_t, a_t, R_t, \mathbf{s}_{t+1})\}$
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[!htbp]
\caption{Threat-Aware Policy Optimization with Auxiliary Risk Regularization}
\label{alg:policy_training}
\begin{algorithmic}[1]
\Require Policy parameters $\theta$, value parameters $\phi$, auxiliary head $\psi$, learning rates $\eta_\pi, \eta_v, \eta_{aux}$, clipping threshold $\epsilon = 0.2$, GAE parameter $\lambda = 0.95$.
\For{iteration $k = 1, 2, \dots, K$}
    \State Collect batch of trajectories $\mathcal{D}_k$ by executing $\pi_{\theta_{old}}$ with threat-adaptive temperature $\tau_{temp}(\mathbf{s}_t)$
    \State Compute Generalized Advantage Estimates $\hat{A}_t$ and discounted returns $\hat{R}_t$:
    \State \quad $\delta_t^V = R_t + \gamma V_\phi(\mathbf{s}_{t+1}) - V_\phi(\mathbf{s}_t)$
    \State \quad $\hat{A}_t = \sum_{l=0}^{\infty} (\gamma \lambda)^l \delta_{t+l}^V$
    \State Normalize advantages: $\hat{A}_t \leftarrow (\hat{A}_t - \mu_{\hat{A}}) / (\sigma_{\hat{A}} + 10^{-8})$
    \For{epoch $e = 1, \dots, E$}
        \State Compute probability ratios $r_t(\theta) = \frac{\pi_\theta(a_t \mid \mathbf{s}_t, \tau_{temp})}{\pi_{\theta_{old}}(a_t \mid \mathbf{s}_t, \tau_{temp})}$
        \State Compute clipped surrogate objective:
        \State \quad $\mathcal{L}_{clip}(\theta) = \hat{\mathbb{E}}_t \left[ \min\left(r_t(\theta)\hat{A}_t, \text{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon)\hat{A}_t\right) \right]$
        \State Compute value function squared error loss:
        \State \quad $\mathcal{L}_{val}(\phi) = \hat{\mathbb{E}}_t \left[ (V_\phi(\mathbf{s}_t) - \hat{R}_t)^2 \right]$
        \State Compute auxiliary next-step risk prediction loss (Training Only):
        \State \quad $\mathcal{L}_{aux}(\psi) = \hat{\mathbb{E}}_t \left[ \|\hat{\mathbf{y}}_t(\psi) - \mathbf{y}_{t+1}^*\|_2^2 \right]$ where $\mathbf{y}_{t+1}^* = [\mathbf{r}_{t+1}^{(0:4)}, a_{t+1}]^T$
        \State Total composite objective: $\mathcal{L}_{total} = -\mathcal{L}_{clip}(\theta) + c_1 \mathcal{L}_{val}(\phi) + c_2 \mathcal{L}_{aux}(\psi) - \beta_{ent} \mathcal{H}(\pi_\theta)$
        \State Update parameters via gradient descent with norm clipping $\|\nabla\|_2 \le 0.5$:
        \State \quad $\theta \leftarrow \theta - \eta_\pi \nabla_\theta \mathcal{L}_{total}, \quad \phi \leftarrow \phi - \eta_v \nabla_\phi \mathcal{L}_{total}, \quad \psi \leftarrow \psi - \eta_{aux} \nabla_\psi \mathcal{L}_{total}$
    \EndFor
    \State $\theta_{old} \leftarrow \theta$
\EndFor
\State \Return Optimized parameters $\theta^*, \phi^*, \psi^*$
\end{algorithmic}
\end{algorithm}

\subsection{Microservice Benchmark Topology}
We model a 7-service enterprise e-commerce microservice topology structured after industry-standard benchmarks (Google Online Boutique and Sock Shop)~\cite{aderaldo2025declarative, soldani2023microservice}:
\begin{itemize}
    \item \textbf{Gateway:} Ingress router and TLS termination point (vulnerable to $F_1, F_8$).
    \item \textbf{Authentication:} Token validation and session manager (vulnerable to $F_4, F_5$).
    \item \textbf{User Service:} Customer profiles and data store (vulnerable to $F_2, F_3$).
    \item \textbf{Order Service:} Checkout and order orchestration (vulnerable to $F_6$).
    \item \textbf{Payment Service:} Payment processing gateway.
    \item \textbf{Inventory Service:} Stock management and warehouse tracking (vulnerable to $F_7$).
    \item \textbf{Notification Service:} Customer communication and alerting.
\end{itemize}

\subsection{Baseline Policies for Comparison}
To comprehensively evaluate SecChaos-RL's software engineering utility, we evaluate eight distinct mitigation policies operating under identical environmental conditions:
\begin{enumerate}
    \item \textbf{No-Mitigation Policy:} Passive failure baseline. Quantifies the natural degradation trajectory when faults accumulate unmanaged.
    \item \textbf{Static Rule-Based Policy:} Deterministic greedy automation. Immediately triggers the prescribed mitigation action upon detecting an elevated risk alert ($r_i > 0.35$), dispatching actions without queue introspection.
    \item \textbf{Threshold-Based Policy:} Industry-standard DevOps SRE heuristic. Triggers mitigations only when risk crosses $\theta_{risk} > 0.35$ and cluster CPU is not currently spiking ($u_{cpu} < 0.85$).
    \item \textbf{Queue-Aware Cooldown Heuristic:} Enhanced DevOps heuristic incorporating action queue introspection and cooldown timers ($t_{cool} = 2$ steps). Prevents dispatching redundant mitigations if an action targeting the same service is already pending in $\mathcal{Q}$ or currently on cooldown.
    \item \textbf{Deep Q-Network (DQN)~\cite{mnih2015human}:} Off-policy value-based RL agent with experience replay buffer ($10,000$ transitions) and target network updates.
    \item \textbf{Advantage Actor-Critic (A2C)~\cite{mnih2016asynchronous}:} Synchronous on-policy actor-critic architecture.
    \item \textbf{Standard PPO~\cite{schulman2017ppo}:} Standard Proximal Policy Optimization with clipping ($\epsilon = 0.2$), GAE ($\lambda = 0.95$), and standard MLP policy.
    \item \textbf{SecChaos-RL (Proposed):} Full architecture with multi-head self-attention, threat-aware gating, auxiliary risk head, and adaptive temperature exploration.
\end{enumerate}

\subsection{Six-Stage Ablation Configurations}
To answer RQ3 and isolate the independent empirical contribution of each architectural component, we evaluate six incremental configurations across all 30 random seeds:
\begin{itemize}
    \item \textbf{Stage 1 (Baseline PPO):} Standard PPO with standard MLP policy and unweighted reward, corresponding identically to the PPO baseline in the comparative benchmark.
    \item \textbf{Stage 2 (PPO + SecReward):} PPO utilizing our multi-objective security resilience reward function (Eq.~\ref{eq:reward_function}).
    \item \textbf{Stage 3 (PPO + SecReward + Attention):} Incorporating Multi-Head Self-Attention ($d_k=16$, embed\_dim=32) over projected telemetry embeddings to capture non-local service dependencies.
    \item \textbf{Stage 4 (PPO + SecReward + Attention + AuxRisk):} Adding the auxiliary next-step risk prediction head as a training-time inductive regularizer.
    \item \textbf{Stage 5 (PPO + SecReward + Attention + AuxRisk + Gating):} Introducing Threat-Aware Feature Gating to dynamically prioritize security-critical telemetry during active emergencies, isolating gating from exploration dynamics.
    \item \textbf{Stage 6 (Full SecChaos-RL):} Complete framework incorporating Threat-Adaptive Temperature Exploration, corresponding identically to the proposed SecChaos-RL policy in the main benchmark.
\end{itemize}

\subsection{Training and Evaluation Protocol}
\begin{itemize}
    \item \textbf{Curriculum Progression:} Agents are trained across 250 episodes ($50$ steps/episode, totaling $12,500$ operational steps per seed) progressing through four difficulty stages: Phase 0 (Episodes 0–40, baseline faults $F_1, F_5$), Phase 1 (Episodes 40–90, faults $F_1 \dots F_5$, 1 attack), Phase 2 (Episodes 90–150, faults $F_1 \dots F_6$, 2 attacks), and Phase 3 (Episodes 150–250, all faults $F_1 \dots F_8$, 4 attacks, active cascading propagation).
    \item \textbf{Evaluation Benchmark:} Every policy is evaluated across 20 held-out evaluation episodes per seed ($1,000$ decisions per seed) strictly under \textbf{Phase 3 (Critical Chaos)} to test maximum resilience under extreme turbulence. Matched environmental conditions and identical fault realizations are guaranteed by seeding the evaluation environment deterministically ($seed + 500$).
    \item \textbf{Hardware Testbed Specification:} Experiments were executed on a dedicated workstation equipped with a 13th Gen Intel Core i7-13700 processor (16 physical cores, 24 threads, up to 5.2 GHz), 16 GB DDR5 RAM, running Ubuntu 22.04 LTS (Linux kernel 6.8.0), Python 3.10.12, and PyTorch 2.12.0+cu130.
    \item \textbf{Statistical Rigor for Repeated-Seed Design:} Exactly 30 independent random seeds are executed (`range(2026, 2056)`). Because policies are evaluated under identical environmental seeds, observations are naturally paired. We conduct Repeated-Measures ANOVA across all algorithms, paired $t$-tests and Wilcoxon signed-rank tests for pairwise comparisons against SecChaos-RL, report 95\% confidence intervals for paired differences, and compute paired Cohen's $d$ effect sizes.
\end{itemize}

\subsection{Quantitative Resilience Metrics}
\begin{enumerate}
    \item \textbf{Security Risk Reduction (\%):} Evaluated as the signed relative change in mean risk relative to the unmitigated failure baseline under the identical environmental seed:
    \begin{equation}
        \Delta \mathcal{L}_{sec} = \left(\frac{\bar{r}_{unmitigated} - \bar{r}_{policy}}{\max(\bar{r}_{unmitigated}, 10^{-6})}\right) \times 100\%
    \end{equation}
    where $\bar{r}_{policy}$ and $\bar{r}_{unmitigated}$ represent average risk across all five vulnerability domains and all time steps ($t \in [1, T]$). Notice that this signed formulation permits negative values if an aggressive policy degrades security relative to unmanaged failure; evaluating under matched environmental seeds guarantees that the unmitigated reference baseline strictly achieves $\Delta \mathcal{L}_{sec} = 0.00\% \pm 0.00\%$ by definition.
    \item \textbf{Service Availability (\%):} Mean percentage of uptime and request fulfillment across all microservices ($\bar{a} \times 100\%$).
    \item \textbf{Mean Time to Recovery (MTTR):} Average number of steps required to return to normal health ($a \ge 0.90, \bar{r} \le 0.45$) following degradation.
    \item \textbf{Attack Success Rate (ASR \%):} Percentage of operational steps where active attacker sessions successfully compromised a service.
    \item \textbf{False Mitigation Rate (FMR \%):} Proportion of deployed non-idle mitigations that were unnecessary or mismatched:
    \begin{equation}
        \text{FMR} = \frac{N_{wrong}}{\max(1, N_{actions})} \times 100\%
    \end{equation}
    where $N_{actions}$ is total non-idle mitigations dispatched and $N_{wrong}$ counts actions dispatched when no active fault matches the target and targeted risk is below $0.30$. We report both FMR and absolute action counts ($N_{actions}$ and $N_{wrong}$ per episode) to distinguish action frequency from proportional precision.
    \item \textbf{Decision Latency (ms):} End-to-end controller duration in milliseconds (feature processing, inference, and action selection) measured via \texttt{time.perf\_counter()} over 2,000 timed decisions following a 100-step warm-up.
    \item \textbf{Holistic Resilience Score (\%):} Composite system survivability index evaluated per seed $k$:
    \begin{equation}
        \mathcal{R}_k = 0.4 \Delta \mathcal{L}_{sec, k} + 0.4 \bar{a}_k + 0.2 \left(\frac{100}{1 + \text{MTTR}_k}\right)
    \end{equation}
    The reported score is the sample mean $\bar{\mathcal{R}} = \frac{1}{N}\sum_{k=1}^N \mathcal{R}_k$ across the $N=30$ seeds. The weights reflect standard SRE balance: $40\%$ weight on security risk reduction ($\Delta \mathcal{L}_{sec}$), $40\%$ weight on operational request fulfillment and service availability ($\bar{a}$), and $20\%$ weight on rapid degradation recovery ($100 / (1 + \text{MTTR})$). Note that because $f(x) = \frac{100}{1+x}$ is a strictly convex function for $x > -1$, by Jensen's inequality $\mathbb{E}[f(x)] > f(\mathbb{E}[x])$; thus, evaluating Eq.~(15) using aggregate column means yields $44.94\%$, whereas the true sample mean of per-seed resilience is $45.21\% \pm 2.26\%$.
\end{enumerate}

\subsection{RQ1: Resilience and Recovery Efficacy}
Table~\ref{tab:rl_resilience_results} and Figure~\ref{fig:resilience_benchmarking} present the quantitative resilience benchmarking results across all eight evaluated policies over 30 independent random seeds under Phase 3 (Critical Security Chaos). Table~\ref{tab:paired_statistical_results} details the formal paired statistical hypothesis tests comparing SecChaos-RL against each baseline under identical environmental realizations, reporting both unadjusted $p$-values and Holm-Bonferroni adjusted $p$-values across the seven pairwise comparisons.

In the absence of automated remediation (\textbf{No-Mitigation}), security chaos causes severe service degradation: the unmanaged system achieves $0.0\% \pm 0.0\%$ risk reduction by definition, sustains an attack success rate of $35.2\% \pm 2.2\%$, an MTTR of $1.24 \pm 0.58$ steps (reflecting passive recovery of transient faults), and records an average resilience score of $45.7\% \pm 2.1\%$.

The deterministic \textbf{Rule-Based} policy achieves substantial risk reduction ($55.5\% \pm 4.8\%$) and a resilience score of $68.3\% \pm 2.6\%$ by greedily dispatching mitigations upon detecting alert signals. However, as analyzed in Section~\ref{subsec:rq2_availability}, this aggressive triggering comes at the expense of severe operational redundancy (deploying actions at literally every step, $50.0 \pm 0.1$ actions/ep, with $15.4 \pm 2.5$ wrong actions per episode, $\text{FMR} = 30.8\% \pm 4.9\%$). In contrast, the \textbf{Threshold-Based} heuristic achieves $19.8\% \pm 3.4\%$ risk reduction, $92.9\% \pm 0.4\%$ availability, and an MTTR of $2.29 \pm 0.30$ steps, deploying $28.1 \pm 1.3$ actions per episode with minimal false dispatches ($0.04 \pm 0.04$ wrong actions/ep, $\text{FMR} = 0.15\% \pm 0.15\%$).

The \textbf{Queue-Aware Cooldown Heuristic} incorporates queue introspection and cooldown timers ($t_{cool}=2$ steps), achieving $26.3\% \pm 2.9\%$ risk reduction and $93.5\% \pm 0.3\%$ availability with only $17.0 \pm 0.8$ actions per episode ($0.02 \pm 0.03$ wrong actions/ep, $\text{FMR} = 0.11\% \pm 0.18\%$). However, its fixed cooldown timers prevent immediate response to recurrent or mutating cascading faults, resulting in an MTTR of $2.24 \pm 0.23$ steps.

Among reinforcement learning baselines, standard \textbf{DQN}, \textbf{A2C}, and \textbf{PPO} achieve risk reductions of $3.5\% \pm 4.9\%$, $4.4\% \pm 4.3\%$, and $4.8\% \pm 3.5\%$, respectively, with overall resilience scores of $45.1\% \pm 2.5\%$, $45.6\% \pm 2.6\%$, and $45.9\% \pm 2.3\%$. Under extreme multi-stage chaos (8 concurrent fault types, 4 active attack sessions), standard model-free RL algorithms struggle with delayed execution credit assignment: the temporal lag between action dispatch and risk restoration ($d_k \in \{0, 1, 2\}$) dilutes policy gradient updates across the 9-dimensional action space.

\textbf{SecChaos-RL} demonstrates measurable recovery speed advantages over heuristic automation. Specifically, SecChaos-RL achieves a Mean Time to Recovery of $\mathbf{\text{MTTR} = 1.79 \pm 0.53}$ steps, significantly accelerating recovery compared to:
\begin{itemize}
    \item \textbf{Threshold-Based:} SecChaos-RL reduces recovery latency by $\Delta = -0.495$ steps ($95\%\ \text{CI} = [-0.734, -0.257]$, paired-$t = -4.25, p_{raw} = 0.0002, p_{holm} = 0.0013$; Wilcoxon $W = 67, p = 0.0003$; Cohen's $d = -0.78$).
    \item \textbf{Queue-Aware Cooldown:} SecChaos-RL reduces recovery latency by $\Delta = -0.454$ steps ($95\%\ \text{CI} = [-0.672, -0.237]$, paired-$t = -4.28, p_{raw} = 0.0002, p_{holm} = 0.0013$; Wilcoxon $W = 64, p = 0.0003$; Cohen's $d = -0.78$).
    \item \textbf{Rule-Based and RL Baselines:} Compared to Rule-Based ($\Delta = +0.175$ steps, $p_{holm} = 0.3736$) and standard PPO ($\Delta = +0.114$ steps, $p_{holm} = 0.9195$), A2C ($\Delta = +0.061$ steps, $p_{holm} = 1.0000$), and DQN ($\Delta = +0.047$ steps, $p_{holm} = 1.0000$), SecChaos-RL achieves statistically comparable recovery time while avoiding the severe action storming of static greedy rules ($35.3$ vs. $50.0$ actions/ep).
\end{itemize}

\textbf{Repeated-Measures ANOVA:} Because all eight policies were evaluated across identical random seeds, a Repeated-Measures ANOVA accounting for within-seed pairing was conducted across all 30 seeds ($df_1 = 7, df_2 = 203$). The analysis confirms highly significant overall policy variance:
\begin{itemize}
    \item Composite Resilience Score: $F(7, 203) = 521.00, p < 0.0001$ ($p = 5.52 \times 10^{-126}$).
    \item Mean Time to Recovery (MTTR): $F(7, 203) = 17.52, p < 0.0001$ ($p = 4.34 \times 10^{-18}$).
    \item Security Risk Reduction: $F(7, 203) = 1092.41, p < 0.0001$ ($p = 2.33 \times 10^{-157}$).
    \item Service Availability: $F(7, 203) = 501.95, p < 0.0001$ ($p = 1.97 \times 10^{-124}$).
    \item Attack Success Rate: $F(7, 203) = 402.12, p < 0.0001$ ($p = 2.88 \times 10^{-115}$).
    \item False Mitigation Rate: $F(7, 203) = 287.38, p < 0.0001$ ($p = 1.18 \times 10^{-101}$).
\end{itemize}

Crucially, the data demonstrate that SecChaos-RL does not claim universal dominance across every individual outcome: rather, its primary empirical contribution lies in rapid recovery (MTTR) under cascading failure without succumbing to the severe mitigation storms of greedy static rules.

\textbf{Analysis of Mitigation Frequency and FMR:} While the Rule-Based policy achieves high security risk reduction ($55.5\%$), it deploys actions at virtually every operational step ($50.0 \pm 0.1$ actions per 50-step episode), resulting in $15.4 \pm 2.5$ wrong actions per episode ($\text{FMR} = 30.8\% \pm 4.9\%$). Because static alert-matching rules lack execution queue awareness and cluster resource introspection, they continuously dispatch redundant mitigations for already-queued operations, inducing CPU and memory contention. 

Conversely, the Threshold-Based heuristic minimizes false mitigations ($0.15\% \pm 0.15\%$) by enforcing resource guards and waiting for sustained risk crosses, deploying $28.1 \pm 1.3$ actions per episode ($0.04 \pm 0.04$ wrong actions). To test whether improved action scheduling alone could resolve this dilemma, we evaluated the \textbf{Queue-Aware Cooldown Heuristic}: introducing queue introspection and cooldown timers ($t_{cool}=2$) reduced action deployment to $17.0 \pm 0.8$ actions/ep with $0.02 \pm 0.03$ wrong actions/ep ($\text{FMR} = 0.11\% \pm 0.18\%$), but MTTR remained elevated at $2.24 \pm 0.23$ steps. Fixed cooldown timers prevent the system from reacting when faults recur or mutate during the cooldown window.

Under reinforcement learning control, DQN, A2C, and PPO deploy $34.2$ to $34.7$ actions per episode with false mitigation rates of $20.4\%$, $22.0\%$, and $21.7\%$ ($7.2$ to $7.8$ wrong actions per episode). SecChaos-RL achieves a balanced profile: deploying $35.3 \pm 3.0$ actions per episode with $7.5 \pm 1.9$ wrong actions ($\text{FMR} = 20.9\% \pm 4.4\%$) while maintaining service availability at $90.6\% \pm 0.5\%$.

\section{Discussion and Practical Implications}
\label{sec:discussion}

The empirical findings provide important insights for software engineers, site reliability engineers (SREs), and DevSecOps practitioners:

\subsection{When Is Autonomous RL Mitigation Superior to Static Rules?}
Our comparative results reveal clear boundaries regarding when adaptive RL is justified over simpler rule-based automation:
\begin{itemize}
    \item \textbf{Under Low Turbulence and Isolated Faults:} When security faults occur infrequently and affect independent services without downstream dependencies, static rule heuristics perform acceptably with negligible overhead. In simple architectures, introducing deep RL adds unnecessary complexity.
    \item \textbf{Under Concurrent Chaos and Cascading Topologies:} When multiple faults occur simultaneously across interdependent microservices (as in modern Kubernetes clusters), static rules fail catastrophically: they trigger alert storms, deploy redundant actions ($30.8\%$ false mitigation rate, $15.4$ wrong actions/ep), and exhaust cluster resources. SecChaos-RL is specifically valuable in these complex settings, where it sequences mitigations intelligently, prioritizing upstream bottleneck services (such as Gateway and Authentication) to halt cascading failures while safeguarding availability SLAs.
\end{itemize}

\subsection{Industrial Deployment Roadmap for Kubernetes}
SecChaos-RL's modular architecture was designed to facilitate direct integration with cloud-native orchestration tooling as an autonomous Kubernetes Operator:
\begin{enumerate}
    \item \textbf{Telemetry Ingestion Pipeline:} The 16-dimensional observation vector can be collected continuously in production by querying Prometheus time-series metrics (CPU, memory, request error rates) and distributed OpenTelemetry traces via Envoy service mesh sidecars, aggregating telemetry within a 1-second sliding window.
    \item \textbf{Chaos Experimentation Engine:} The \texttt{ChaosEngine} directly mirrors Kubernetes Custom Resource Definitions (CRDs) standardized by open-source chaos frameworks such as Chaos Mesh and LitmusChaos. In pre-production staging clusters, the engine automates scheduled chaos experiments (network partition injection, CPU throttling, certificate corruption) to validate policy robustness.
    \item \textbf{Kubernetes Operator Remediation Controller:} The \texttt{MitigationExecutor} can be implemented as a custom Kubernetes Operator written in Go (using the \texttt{operator-sdk}), translating discrete policy actions into standard Kubernetes API operations:
    \begin{itemize}
        \item Action 1--3 (Isolate/Heal Service): Patches \texttt{NetworkPolicy} objects to sever ingress traffic to compromised pods while maintaining egress for state draining.
        \item Action 4 (Renew Certificates): Triggers automated certificate re-issuance via \texttt{cert\allowbreak-manager} CRDs.
        \item Action 5 (Flush Session Cache): Dispatches Redis/Keycloak cache flush commands via targeted executive jobs.
        \item Action 6--8 (Restart/Scale Workloads): Initiates controlled rolling pod restarts or horizontal replica scaling via \texttt{apps/v1} Deployment patches.
    \end{itemize}
\end{enumerate}

\subsection{Operational Safety Safeguards for Autonomous Remediation}
Deploying autonomous reinforcement learning controllers in mission-critical microservice environments introduces non-trivial operational risks, including mitigation storms, flapping, and unintended resource exhaustion. To ensure safe production deployment, SecChaos-RL incorporates five layered runtime safeguards:
\begin{enumerate}
    \item \textbf{Pre-Flight Action Verification:} Before executing any remediation API call, the operator verifies cluster admission conditions: target pod existence, node resource headroom, and control plane responsiveness. If pre-flight assertions fail, the action is aborted, preventing deadlocked mutation loops.
    \item \textbf{Bounded Retry Budgets and Back-Off:} To prevent infinite restart loops when a root-cause bug persists, the controller enforces strict retry budgets (maximum 3 mitigation attempts per service within a 10-minute sliding window) with exponential back-off.
    \item \textbf{Dynamic Rate-Limiting and Circuit Breakers:} If the aggregate mitigation dispatch rate across the cluster exceeds safe thresholds ($> 5$ mutations per minute), or if cluster-wide request error rates spike by more than $15\%$ following an intervention, an emergency circuit breaker trips, instantly freezing autonomous mutations and reverting to read-only monitoring.
    \item \textbf{Automated Health Rollbacks:} Following every mitigation action, the controller monitors downstream service latency and error budgets for 30 seconds. If service degradation intensifies, the operator triggers an automated rollback to the previous known-good deployment revision via the Kubernetes revision history API.
    \item \textbf{Human-in-the-Loop Overrides (Break-Glass Latch):} Autonomous execution can be suspended at any moment via an administrative break-glass switch exposed through Slack and PagerDuty webhook integrations, allowing on-call SREs to audit recent decision histories and assume manual control during unexpected incidents.
\end{enumerate}

\section{Threats to Validity}
\label{sec:validity}

\textbf{Construct Validity:} Construct validity concerns whether our evaluation metrics accurately reflect software resilience. We addressed this by combining multiple orthogonal software engineering measurements: signed security risk reduction, live service availability, MTTR, attack success rate, false mitigation rate, absolute action counts ($N_{actions}, N_{wrong}$), and decision latency percentiles. To avoid hiding negative outcomes, risk reduction was evaluated as signed relative change without zero-clipping, ensuring that policies degrading security relative to unmanaged failure exhibit negative percentages. Furthermore, we mathematically clarified that composite resilience score discrepancies between aggregate column means and reported tables arise from Jensen's inequality over the convex recovery function $f(\text{MTTR}) = 100 / (1 + \text{MTTR})$.

\textbf{Internal Validity:} Internal validity addresses whether the observed gains are genuinely caused by our architectural design. We mitigated potential bias by evaluating all eight policies under strictly matched environmental seeds, ensuring identical fault realizations across comparative evaluations. We implemented standardized curriculum progressions and conducted a six-stage ablation study isolating each architectural innovation with paired difference intervals ($95\%$ CI).

\textbf{External Validity:} External validity concerns the generalizability of our findings to production enterprise microservices. Our experiments were conducted within an architectural simulation modeled after industry-standard benchmarks (Google Online Boutique and Sock Shop)~\cite{aderaldo2025declarative, soldani2023microservice}. While our simulation faithfully models cascading topological failures, asynchronous execution delays, and cluster resource contention, live production clusters introduce non-deterministic network jitter, persistent volume I/O throttling, and database lock contention. Transitioning SecChaos-RL from high-fidelity simulation to a live, containerized Kubernetes testbed represents a primary avenue for ongoing development.

\textbf{Conclusion Validity:} Conclusion validity was reinforced by evaluating exactly 30 independent random seeds, conducting Repeated-Measures ANOVA across all eight policies ($F(7, 203), p < 0.0001$) to match the matched-seed experimental design, and reporting paired $t$-tests, Wilcoxon signed-rank tests, Holm-Bonferroni adjusted $p$-values, 95\% confidence intervals of paired differences, and Cohen's $d$ effect sizes.

\section{Conclusion and Future Work}
\label{sec:conclusion}

This paper introduced \textbf{SecChaos-RL}, an autonomous, threat-aware resilience engineering framework that unifies Security Chaos Engineering with deep reinforcement learning for microservice software systems. By formalizing security mitigation as a multi-objective Markov Decision Process and designing a specialized neural policy architecture—incorporating multi-head self-attention, threat-aware feature gating, auxiliary risk prediction, and threat-adaptive temperature exploration—SecChaos-RL addresses the fundamental operational tension between rapid security isolation and microservice availability SLAs.

Rigorous evaluation across 30 independent random seeds and paired statistical testing demonstrate that SecChaos-RL achieves superior recovery speed compared to heuristic automation ($\text{MTTR} = 1.79 \pm 0.53$ steps vs. $2.24 \pm 0.23$ for Queue-Aware Cooldown, $p_{holm} = 0.0013$; and $2.29 \pm 0.30$ for Threshold-Based, $p_{holm} = 0.0013$), reduces false mitigations to $20.9\% \pm 4.4\%$ compared to greedy heuristics ($30.8\% \pm 4.9\%$ for Rule-Based), avoids disruptive action storms ($35.3$ vs. $50.0$ actions/ep), and executes with sub-millisecond decision latency ($0.44 \pm 0.15$\,ms mean). A systematic six-stage ablation study substantiates the incremental contribution of each architectural component, and our comparative findings delineate the practical boundaries between deterministic alert heuristics and adaptive reinforcement learning control in cloud-native software environments.

In future work, we plan to package SecChaos-RL as a production-grade Kubernetes Operator, streaming real-time telemetry from Prometheus and executing chaos experiments via Chaos Mesh on live distributed testbeds. Furthermore, we intend to explore hierarchical multi-agent reinforcement learning to coordinate decentralized mitigation policies across multi-cluster cloud deployments.
